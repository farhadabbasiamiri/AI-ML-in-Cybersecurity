# TriageMate Application Workflow

## 1. Project purpose

TriageMate is a SOC (Security Operations Center) Alert Triage Agent. It helps
security analysts process many security alerts, identify the most important
ones, understand what happened, and decide what to investigate next.

The application is designed for defensive cybersecurity use. It does not
automatically attack, modify, or contain systems. A human analyst must review
and approve an alert before a ticket is created.

## 2. Important terms

### SIEM alert

A security event generated by a monitoring platform such as a firewall,
endpoint security product, Windows event log system, or SIEM.

### Alert triage

The first analysis of an alert. Triage determines whether an alert is benign,
a false positive, or potentially a real security incident.

### Parser

The parser converts different alert formats into one consistent structure. It
extracts fields such as alert ID, timestamp, host, user, source IP, rule name,
severity, and raw log data.

### Rule-based scorer

A deterministic Python component that calculates a risk score using known
signals. It does not depend on the LLM and continues working if the LLM is
unavailable.

### MITRE ATT&CK

MITRE ATT&CK is a knowledge framework describing common attacker behaviors.
For example, deleting shadow copies can be mapped to T1490, Inhibit System
Recovery.

### RAG

RAG means Retrieval-Augmented Generation. The application searches its local
MITRE ATT&CK and SOC playbook knowledge base, then gives the relevant passages
to the LLM so its answer is grounded in project knowledge.

### LLM

LLM means Large Language Model. TriageMate currently uses the Groq API with the
configured model from `.env`. The LLM generates a readable summary, explains
the priority, and recommends safe investigation steps.

### Human-in-the-loop

A human analyst reviews the automated result before a ticket is finalized.
Containment recommendations, such as isolating a host or disabling an account,
require additional approval.

## 3. Complete workflow

```text
Upload alerts
      |
      v
Parse and normalize fields
      |
      v
Calculate deterministic risk score
      |
      v
Map behavior to MITRE ATT&CK
      |
      v
Retrieve relevant MITRE and playbook knowledge
      |
      v
Display alerts in the queue
      |
      v
Request AI analysis
      |
      v
Generate summary, priority reason, and safe next steps
      |
      v
Analyst reviews and approves
      |
      v
Create a structured JSON ticket
      |
      v
Display dashboard and evaluation results
```

## 4. Detailed application flow

### Step 1: Application startup

The application starts from `app.py`. It loads the Gradio interface, alert
pipeline, RAG knowledge base, dashboard, and configured LLM provider.

The LLM configuration is read from the project-root `.env` file:

```text
LLM_PROVIDER=groq
LLM_MODEL=<configured Groq model>
GROQ_API_KEY=<private API key>
```

The API key must never be included in this document or committed to Git. The
project ignores `.env` through `.gitignore`.

### Step 2: Alert ingestion

The analyst opens the Upload tab and uploads a JSON Lines alert file. If no
file is uploaded, the application uses the sample data at:

```text
data/all_alerts.jsonl
```

### Step 3: Parsing and normalization

`triage/parser.py` converts nested or inconsistent alert data into standard
fields. This allows all alerts to be processed in the same way.

Typical normalized fields include:

- Alert ID
- Timestamp
- Host
- User
- Source IP
- Rule name
- Log source
- Vendor severity
- Raw log
- Data source

### Step 4: Rule-based scoring

`triage/scorer.py` examines the normalized alert. It checks suspicious
keywords, vendor severity, external IP addresses, ransomware indicators,
credential attack indicators, lateral movement indicators, and benign patterns.

The scorer produces:

```text
score
priority
category_guess
reasons
```

For example, an alert containing `vssadmin delete shadows` may receive a high
priority because deleting shadow copies is associated with ransomware activity.

### Step 5: MITRE ATT&CK mapping

`triage/mitre.py` searches the alert text for known behavior patterns and maps
them to a MITRE ATT&CK technique.

Example:

```text
vssadmin delete shadows
```

can be mapped to:

```text
T1490 - Inhibit System Recovery
Tactic: Impact
```

### Step 6: RAG retrieval

`triage/rag.py` searches the project knowledge base for relevant information.
The knowledge base contains MITRE technique descriptions and SOC
investigation playbook guidance.

For example, an alert involving LSASS memory access may retrieve guidance about
credential dumping, process creation logs, account activity, and host
investigation.

### Step 7: Alert queue

After deterministic processing, alerts appear in the Alert Queue tab. The
queue shows the alert ID, rule priority, score, category, MITRE technique,
host, and AI priority when available.

Higher-risk alerts are shown first so the analyst can focus on the most
important alerts.

### Step 8: AI analysis

When the analyst selects an alert and clicks **Run AI analysis**, or runs AI
analysis over a queue, `triage/llm.py` sends the following information to
Groq:

- Normalized alert fields
- Rule-based score and priority
- Category
- MITRE technique
- Retrieved RAG knowledge
- Relevant raw log content

The LLM is instructed to return structured JSON containing:

```json
{
  "summary": "Plain-English explanation of what happened",
  "priority": "Low|Medium|High|Critical",
  "priority_reason": "Reason for the priority",
  "next_steps": [
    "Safe investigation step 1",
    "Safe investigation step 2",
    "Safe investigation step 3"
  ]
}
```

The application adds the RAG citations and displays the result in the Alert
Detail tab.

### Step 9: Fallback behavior

If Groq is unavailable, the API key is invalid, the request times out, or the
response cannot be parsed, the application uses a predefined rule-based
explanation instead of crashing.

The result is labelled as a rule-based fallback. This means the core
application continues to work even when the LLM is offline.

### Step 10: Alert detail and tool trace

The Alert Detail tab displays:

- Alert ID and priority
- Risk score
- Rule name
- Category
- MITRE ATT&CK mapping
- Host, user, and source IP
- Raw log
- Rule-based reasons
- AI summary
- AI priority and reason
- Safe next steps
- RAG citations

The tool trace shows the processing sequence:

```text
Parser -> Scorer -> MITRE lookup -> RAG retrieval -> LLM analysis
```

### Step 11: Human review and approval

The analyst reviews the rule-based result and AI explanation. The application
requires AI analysis to be run before approval.

The analyst must confirm that the alert was reviewed. If the recommended steps
mention containment, an additional containment approval is required.

TriageMate does not automatically isolate hosts, disable accounts, block
traffic, or perform other system changes.

### Step 12: Ticket creation

After approval, the application creates a structured JSON ticket containing
information such as:

- Alert ID
- Priority
- Score
- Category
- MITRE technique
- Summary
- Priority reason
- Recommended next steps
- RAG citations
- Approval status
- Containment approval status

### Step 13: Dashboard

The Dashboard tab summarizes the current alert batch. It displays alert
priorities, categories, MITRE techniques, rule-versus-AI priorities, and
approved alerts.

### Step 14: Evaluation

`eval/evaluate.py` evaluates the deterministic baseline against the labelled
answer key. It reports category accuracy, priority precision, priority recall,
F1 score, and High/Critical recall.

The unit tests in `tests/test_pipeline.py` verify parser behavior, scoring,
MITRE mapping, RAG retrieval, and fallback behavior.

## 5. How to explain the design to teammates

TriageMate is a hybrid system:

```text
Deterministic Python tools = reliable analysis
Groq LLM                  = explanation and recommendations
Human analyst             = final approval
```

The LLM does not replace the entire security pipeline. The parser, scorer,
MITRE mapper, and RAG retriever run first. The LLM then uses their outputs to
produce a grounded explanation. This design makes the system safer,
explainable, and usable even when the LLM is unavailable.

## 6. Short presentation explanation

> TriageMate helps SOC analysts process large numbers of security alerts.
> First, it normalizes each alert and applies a deterministic rule-based risk
> scorer. It then maps suspicious behavior to MITRE ATT&CK and retrieves
> relevant investigation guidance using RAG. Groq generates a concise summary,
> explains the priority, and recommends safe next steps. The analyst reviews
> the result and must approve it before a structured JSON ticket is created.
> If Groq is unavailable, the application uses a rule-based fallback so the
> workflow continues safely.
